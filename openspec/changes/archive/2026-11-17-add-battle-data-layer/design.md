# Design

## Context

The app foundation runs (see the `app-foundation` spec) but persists nothing. Exploration settled the battle architecture before this change: a durable/ephemeral split in which the database stores facts that outlive a battle — identity, membership, configuration snapshots, scrambles, solves, one phase checkpoint per battle — while a later WebSocket runtime owns live state (phases, deadlines, ready sets) in memory. This change builds only the durable half, completely, so the follow-up changes (`add-lobby-api`, then `add-realtime-battles`) are pure logic with zero DDL.

Battle-domain behavior decisions already made (see proposal for motivation):

- Guests get identity rows with a stable id and a token credential; rows stay claimable by a future account.
- Battles snapshot room settings at start; rooms are reusable containers.
- Times live in a `solves` table keyed one-per-round-per-participant, with penalties; final times are derived.
- A single per-battle checkpoint row bridges server-restart resync for the future runtime; ready flags are never persisted.
- Write volume is tiny and batched at phase transitions, which informed the engine choice below.

## Goals / Non-Goals

**Goals:**

- All eight battle-domain tables, with constraints, in one initial migration.
- A typed database client importable from TanStack Start server functions.
- A reproducible local setup: one env var, one migrate command.
- Migrations as the only path by which the schema changes.

**Non-Goals:**

- No routes, server functions, or UI (changes 2 and 3).
- No realtime state, timers, or gate logic (change 3).
- No auth infrastructure or account claiming (a later change fills in the nullable claim fields).
- No Nitro plugin, no deployment/hosting configuration (deferred until the realtime change needs WS).
- No seed data, no scoring/standings computation (derived at read time later, not stored).
- No Zod or scramble generation (arrive with the lobby API change).

## Decisions

### SQLite via libsql, Drizzle ORM, drizzle-kit

Write pattern is a handful of rows per round, batched at transitions — SQLite's weak spot (concurrent writers) is never stressed, and there is one less service to operate. The libsql driver connects to a local `file:` URL in development and speaks the same protocol as Turso, so a future move to a hosted database is a connection-string change, not a code change. Drizzle is the documented TanStack Start pairing: the schema is TypeScript, migrations come from `drizzle-kit`, and types flow into queries without a codegen step.

Alternatives: Postgres/Neon (a second service to run, plus a pooler, for a write volume that never needs it); `better-sqlite3` (synchronous, and no managed-database path).

### All eight tables in the first migration

The schema was designed as a whole during exploration; creating it in one migration keeps foreign-key relationships complete from day one and leaves changes 2 and 3 with zero DDL. The honest alternative — tables arriving only when their writer lands — trades one migration file now for three migrations later, each blocking the change that needs it.

### Identity: stable UUIDs, unique token, nullable claim

`users.id` is a text UUID generated by the application (`crypto.randomUUID()`), never reused; `token` is unique and becomes the httpOnly-cookie value in the lobby change; `claimed_at` is nullable and stays null until a future accounts change fills it. Nothing else links to anything but `id`, so claiming is an update to one row.

Alternatives: integer autoincrement ids (enumerable, and awkward to keep stable across a future claim); issuing tokens as a separate sessions table (deferred until cubers need multiple devices — one row, one device is enough for now).

### Configuration as a JSON snapshot column

`rooms.settings` is a JSON object the host edits; `battles.settings` is a copy of it taken at battle start. Settings are always read as a whole set and never filtered by SQL, so normalization buys nothing — while a JSON column means new settings fields (new event types, new timeout knobs) arrive without a migration.

Alternative considered: battles referencing the room's live settings — rejected in exploration because past battles would quietly rewrite themselves when the host edits settings between games.

### Solves are the only home for times

`solves` keyed `UNIQUE (round_id, user_id)`: `time_ms` is the raw client-reported time, `penalty` is an enum of `none | plus_two | dnf` (csTimer semantics), and final time is always derived — raw + 2000 for a plus-two, no result for DNF. Storing the derived value would lose the raw record; storing times on `rounds` or `users` was rejected in exploration (many cubers per round; times belong to a round of a battle, not to an identity).

### Phase checkpoint: one row per battle, upserted

`phase_checkpoints` is keyed by `battle_id` alone, updated on every transition, holding the current `round_id`, `phase`, and deadline. It exists because phase position cannot be reconstructed from durable facts (solve counts cannot distinguish scramble from inspection), while ready state is cheap to redo — cubers simply re-ready after a restart. Ready flags are therefore deliberately absent from the schema.

### SQLite pragmas: WAL and foreign keys on

The client module enables `journal_mode = WAL` (avoids "database is locked" under concurrent server-function access) and `foreign_keys = ON` (SQLite ships with FK enforcement off by default — without this, the spec's referential-integrity scenarios would not hold). Both are connection-level configuration in `src/db/index.ts`, plus a global-singleton guard so Vite dev hot-reload doesn't open a new connection per module reload.

### Timestamps as UTC unix seconds

Drizzle's `integer { mode: 'timestamp' }` column form: sortable, timezone-unambiguous, and identical in every SQLite tool. Alternative — ISO text — reads nicer in raw queries but sorts lexically and invites format drift.

## Risks / Trade-offs

- **Schema lands before its consumers** → the tables are the recorded contract for changes 2 and 3; this change validates via migrations and typecheck, and the follow-up changes exercise the tables for real.
- **JSON settings are opaque to SQL** → accepted: settings are read as a set and copied wholesale; nothing ever filters on a single setting.
- **FK enforcement depends on connection setup** → mitigated in the client module (pragmas enabled there); the spec's "requires real parents" scenarios verify the behavior.
- **libsql dev driver differences** → the local `file:` driver is the same code path Turso uses; any driver-specific quirk would surface identically in both.

## Migration Plan

`drizzle-kit generate` produces the initial migration from the schema; `pnpm db:migrate` applies it. Fresh clone: `pnpm install` → `pnpm db:migrate` → `pnpm dev`. Rollback in development is deleting `local.db`; there is no production deployment or existing data to migrate yet (greenfield), and the follow-up changes add no DDL of their own.

## Open Questions

- The exact room-settings field list (event ids, timeout values, inspection length) is settled by `add-lobby-api` when its forms exist; the JSON column absorbs new fields without a migration.
- Invite-code format and collision-retry strategy (short alphabetic code vs UUID suffix) is a lobby-change concern; only uniqueness is promised here.
