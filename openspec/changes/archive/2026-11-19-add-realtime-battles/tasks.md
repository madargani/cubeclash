## Implementation notes for the next agent

- **Dev proxy does not rewrite `Sec-WebSocket-Accept`.** The nitro dev server proxies WebSocket upgrades to its dev worker by re-dialing upstream with its own key, and passes the *upstream's* `Sec-WebSocket-Accept` back unchanged. A strict client that validates the accept header against its own key will refuse the handshake; Node's built-in WebSocket (undici) and browsers tolerate it, so this only bites hand-rolled verification clients. If you script a WS client to verify behavior, skip the accept check (as the group-4 dev verification did) and validate behavior by message content instead.
- **Socket layer passes parsed JSON.** `runtime.handleMessage` receives an already-parsed payload object from `websocket.ts` (not a JSON string) — don't re-parse it there. The vitest handler tests feed objects directly to match.
- **One dev server at a time.** Stale `pnpm dev` processes hold ports and serve old code without hot-reloading `src/server/nitro/websocket.ts` changes reliably; restart the dev server after editing the nitro server dir before re-running any scripted verification.
- **Snapshots are read-then-broadcast, never passed through.** The publish helper reads the room's current state once (the same read the room page's loader uses) after a mutation succeeds; it never forwards service return values, so every broadcast stays canonical. The runtime never holds peers — it publishes into the room's channel; connections live only in the peer-keyed channel registry.
- **Two module contexts — registries never cross.** The socket hooks run in the nitro serverDir worker; the TanStack server functions run in the app's SSR bundle. Each context gets its own copy of any module-level Map, so a registry imported by both sides is duplicated, and a publish from the function side silently broadcasts into an empty copy. All channel, runtime, and publish code lives behind the socket route; services and server functions stay registry-free. Never call `RoomRuntime.getOrBuild` from a server function — its timers would fire inside the SSR context and race the real runtime through shared database rows (checkpoints, solves, and the battle's end time).
- **What is already correct — do not rebuild it.** The socket-side modules are implemented and green (all 158 tests pass as of this revision): `channel.ts`, `room-snapshot.ts`, the hooks in `websocket.ts`, the runtime's publish path, and the client hook `src/hooks/use-room-socket.ts`. The live-update defect is entirely on the server-function side — `fns.ts` imports those modules, and those imports resolve to a different copy of the registries. Fix the seam; leave the channel and runtime modules alone.
- **The exact defect sites in `fns.ts`.** Delete the imports from `./nitro/channel`, `./nitro/room-snapshot`, and `./nitro/runtime` at the top of the file. Remove the `publishRoomState` call from `joinRoomFn` — its body becomes: resolve-or-create cuber, `joinRoom`, return `{ roomId }`, publishing nothing (the join announces itself when the joiner's page connects, task 6.5). Delete `updateRoomSettingsFn` and `startBattleFn` entirely, plus `UpdateSettingsInputSchema` (only they used it — `RoomIdInputSchema` stays, `getRoomStateFn` uses it). The reason `startBattleFn` goes entirely: its `RoomRuntime.getOrBuild` call builds a phantom runtime whose timers fire in the SSR context and race the real one through shared database rows.
- **Deleting the two fns breaks the room page until the client switches.** `src/routes/rooms/$roomId.tsx` imports `updateRoomSettingsFn` and `startBattleFn`. Land the fns deletion and the page's switch to socket sends (task 6.4) in the same pass, or `pnpm typecheck` fails in between.
- **Room-level messages dispatch before the runtime lookup.** The `message` hook resolves the runtime first and drops everything when none exists; `updateSettings` and `startBattle` are valid with no battle, so they must be handled at the channel level before that lookup:
  ```
  updateSettings            -> parseRoomSettings -> updateRoomSettings(db, ...) -> publish roomState
  startBattle               -> startBattle(db, ...) -> RoomRuntime.getOrBuild -> publish battleState, then roomState
  ready / submit / forceStart -> runtime lookup as today; route to runtime.handleMessage
  ```
  Both services enforce host and validity themselves (`updateRoomSettings` throws "only the host can change room settings"; `startBattle` throws "only the host can start a battle" and "this room already has an active battle"). Catch their throws and answer the sender with `{ type: 'error', message }`. Validate settings with `parseRoomSettings` from `src/lib/room-settings.ts` — its `z.coerce` fields accept the same raw form values the page sends today.
- **The `startBattle` handler is the runtime's only build site at battle creation.** After task 6.3, a runtime is constructed in exactly two places, both socket-side: the `startBattle` message handler (battle creation) and the open hook (the post-restart rebuild when a battle is active with no runtime). No other code path may call `RoomRuntime.getOrBuild`.
- **Join announce ordering (task 6.5).** In the open hook, broadcast the fresh snapshot to existing peers *before* `channel.open(...)` registers the newcomer, so the newcomer receives exactly one copy; one `getRoomState` read produces the snapshot for both the broadcast and `channel.open`. A refresh or a second tab triggers the same broadcast — harmless, since snapshots replace.
- **StrictMode double-mounts the room socket in dev.** `@tanstack/react-start`'s default client entry wraps the app in `<StrictMode>`, so effects run setup → cleanup → setup. The hook must treat a stale socket's `open`/`message`/`close` events as no-ops (track the effect's own socket): otherwise the discarded socket's close clears `socketRef.current`, every `send` silently drops, and snapshots still arrive so the page looks connected until a reload happens to win the race.
- **Client sends (task 6.4).** `useRoomSocket` already returns `send`. `handleSaveSettings` becomes `send({ type: 'updateSettings', settings: { eventType, roundCount, inspectionSeconds, readyTimeoutSeconds } })`; `handleStartBattle` becomes `send({ type: 'startBattle' })`. Clear the form's pending state when the next `roomState` snapshot arrives; render the socket's `error` string where the old thrown errors rendered; drop the `router.invalidate()` calls — snapshots replace them.
- **Protocol additions (task 2.1).** Extend `ClientMessageSchema`'s discriminated union in `src/server/nitro/protocol.ts` with an `updateSettings` variant carrying a loose `settings` object (validated server-side by `parseRoomSettings`) and a `startBattle` variant with no fields; round-trip tests follow the existing per-message pattern.
- **Suggested order.** 2.1 → 6.3 (scrub `fns.ts` first, then the handlers) → 6.5 → 6.2 (builder tests untouched) → 6.4 last, landing together with the fns deletion.
